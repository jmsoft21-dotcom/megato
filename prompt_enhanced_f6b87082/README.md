# prompt_enhanced_f6b87082 — Triopus CR V3 프롬프트 고도화본

원본 `prompt_originals_f6b87082/`의 역할별 프롬프트 10개를 역할표(`Triopus 모델 우선순위.txt`)와 흐름도(`Triopus_CR_V3_흐름도.webp`)에 맞춰 고도화했습니다. 우선순위는 **고품질 > 토큰 효율 > 속도**입니다. 파일 이름은 원본과 같고, 원본 파일은 수정하지 않았습니다.

- `DESIGN.md`: 고도화 설계서(영문)입니다. 이슈 70건, 우선순위 규칙, 공통 블록 원문, 원본 블록 → 새 블록 매핑, 역할별 사양, 레인 간 동일 정의표, 미결 결정 39건이 들어 있습니다. Host 템플릿(trioplus 코드)에 반영할 때는 3장(공통 블록)과 4장(블록 매핑)을 기준으로 삼으면 됩니다.

## 주요 변경

- **PRECEDENCE_V1:** 모든 파일에 우선순위 규칙을 추가했습니다. 순서는 안전·경계 > Host 봉인 내용 > V2 목표 > 역할 규칙 > 레거시 HTS 기본값입니다. V2 규칙과 레거시 SCORECARD/Bad 라벨 규칙이 충돌하던 문제를 해소했습니다.
- **FLOW_POSITION_V1:** 모든 파일에 흐름도상의 위치를 명시했습니다. 흐름은 사용자 → Grok → GM PLAN → Alpha‖Beta(클린룸) → 합류 → Gamma → GM ANALYZE → 해시 봉인 → Memory 순서입니다.
- **LANE_RESOURCE_SHARE_V1:** Alpha·Beta는 동시에 실행되므로 각각 50%만 씁니다(CPU 12 스레드, RAM 16GB, GPU 8GB 이내). Gamma는 합류 뒤 단독으로 실행됩니다. GM은 계산하지 않습니다. 원본의 "하드웨어 최대 사용" 지시는 이 규칙으로 정의했습니다.
- **bad_rate 분모 통일:** 분모를 `n_resolved`로 통일했습니다. Alpha 지표 계약은 `n_selected`, 과제는 `n_resolved`로 서로 달랐습니다.
- **출력 계약 단일화:** 레인 공통 출력 규칙과 역할별 스키마를 하나로 정리했습니다(GM_PLAN, GM_ANALYZE, Alpha, Beta, Gamma). Beta의 기록 대상 파일 혼선도 해결했습니다. Beta는 `lane_result.json`에 쓰고, Host가 이를 `BETA_LANE_RESULT.json`으로 승격합니다.
- **Gamma:**
  - 다른 레인과 같은 품질 규칙과 실행 규칙을 적용했습니다.
  - 생존 후보가 없을 때의 동작을 정의했습니다.
  - run_lock 감사는 금지된 `evidence.py` 대신 봉인 계약의 `run_lock_v1` 기준으로 합니다.
  - 판정은 5단계로 정의했습니다.
- **Beta:**
  - 모델 바인딩 블록과 Claude CLI 실행 규칙을 추가했습니다.
  - 클린룸에서 확인할 수 없는 교차 레인 조건은 `NOT_EVALUABLE_IN_CLEAN_ROOM`으로 표시합니다.
  - 무엇을 읽었는지 기록(독립성 증빙)하게 했습니다.
- **중단 규칙:** 입력 계약 위반(INPUT_CONTRACT_VIOLATION)과 금지 규칙 위반에서만 중단합니다. 나머지는 발견 사항으로 기록하고 TEST_I2 채점까지 마칩니다. 사이클 1에서 Alpha가 중도에 멈췄던 문제에 대한 대응입니다.
- **DATUM:** 데이터 읽기·추가 허용은 원본대로 유지했습니다. 다만 추가는 이번 사이클에 봉인된 범위(스냅샷, OOS 패킷, 분봉 glob) 밖에서만 하고, 이번 사이클 점수 계산에는 쓰지 않습니다. 사이클 중 기존 파일 수정·삭제는 금지입니다.

  - 예외: ALPHA·BETA에서 일봉 경로 `...\d1_cache.snapshot_666efecf\*.parquet` 1건이 빠졌습니다. 같은 루트를 가리키는 다른 줄과 중복이라 설계에서 허용한 제거입니다.
- 원본에 없던 새 숫자는 0건입니다(역할표의 하드웨어 수치와 그 50% 값은 예외로 허용).
- c1/c2는 Host가 사이클마다 넣는 내용만 다르고 정적 블록은 같습니다.
- 공통 블록은 같은 그룹의 파일끼리 바이트 단위로 같습니다.
- 검증 방법: 설계서 8장의 수용 기준 일부를 자동 점검 스크립트(`check_invariants.py`, `acceptance.py`)로 실행했습니다.
